# SPEC-055 — Фабрики товаров и динамические группы

## Цель

Редактор назначает шаблон опций группе «товары фабрики X» через штатный
product stream. Фабрика означает место производства товара, а не Shopware
manufacturer: у импортированных товаров manufacturer остаётся `JVMOEBEL`.
Пока единственный автоматический источник фабрик — Aftercool Lister.

## Границы

Входят локальный каталог фабрик, одна основная фабрика у товара, связь
Aftercool ID с каталогом, заполнение связи при успешном импорте, перенос
связей ранее импортированных товаров и условие `Фабрика → equals → фабрика`
в редакторе product streams. Список значений фильтра читает только Shopware
DAL; запрос к Aftercool при редактировании stream не выполняется.

Не входят замена `manufacturer`, отдельный публичный Store API, выбор фабрики
покупателем, поиск по всем ещё не импортированным фабрикам Aftercool и
автоматическое объединение разных фабрик с одинаковым названием.

Это backend-local изменение `JvImport`: данные фабрики не принадлежат
`JvProductOptions`. Плагин опций использует штатное сопоставление товара с
product stream согласно SPEC-054 и не читает таблицы `JvImport` напрямую.

## Данные и идентичность

`jv_factory` — Shopware DAL entity с UUID `id` и непустым отображаемым `name`.
Название не является идентификатором и может совпадать у разных фабрик.
Товар имеет nullable `jvFactoryId` и DAL association `jvFactory` на эту
сущность; физическая ссылка в `product` защищена FK и индексом. У товара
не более одной основной фабрики. Вариант без собственного значения наследует
фабрику родителя. Удаление связанной фабрики запрещено до явного отвязывания
товаров и source mapping; «осиротевшего» UUID в товаре быть не должно.

`jv_factory_source` сопоставляет `(sourceNamespace, externalId)` с
`jv_factory.id`, уникально по паре. Для текущего источника namespace —
`aftercool:JV:lister`, external ID — каноническое десятичное представление
положительного целочисленного `factory_id`. Исторические целочисленные поля
Aftercool run, product source link и error не меняются. Отдельное
сопоставление позволяет в будущем связать ту же фабрику с иным источником,
не меняя внутренний ID и товары. Автоматическое сопоставление по имени
запрещено.

Фабрики и source mappings принадлежат `JvImport`. Их определения, миграции
и расширение `product` располагаются в существующих `Core/Content/` и
`Migration/` плагина. Управление через Admin API ограничено штатными правами
на соответствующие сущности; публичный Store API для справочника не нужен.

## Импорт Aftercool

1. `GET /api/import/factories`, preview и постановка run в очередь только
   показывают доступные фабрики; локальную `jv_factory` не создают.
2. На первом checkpoint с хотя бы одним успешно записанным товаром импорт
   находит фабрику по `aftercool:JV:lister` + числовому ID. Если её нет,
   создаёт фабрику и source mapping. Название берётся из проверенного списка
   Aftercool, сохранённого в run, а не из произвольного клиентского текста.
   Создание каталога, запись фабрики на успешные товары, source links и
   checkpoint должны быть атомарны: при сбое не остаётся частичного состояния.
3. Повторный импорт с тем же ID использует тот же UUID фабрики и обновляет
   отображаемое название, если источник переименовал фабрику. Одноимённые
   фабрики с разными внешними ID остаются разными сущностями.
4. Пропущенная, невалидная или отвергнутая Shopware строка не получает связь
   с фабрикой. Полностью пустой/неуспешный импорт не создаёт фабрику.
   Повторная доставка страницы не создаёт дубль и не меняет уже учтённые
   результаты.
5. Для товара с подтверждённой Aftercool source-связью фабрика является
   импортируемым полем. Повторный успешный импорт восстанавливает её связь.
   У товара без Aftercool source-связи редактор может назначить локальную
   фабрику вручную; этот выбор не затрагивается импортом других товаров.
6. Если новый Aftercool source ID разрешается в товар, уже связанный с другой
   фабрикой, импорт не переназначает его молча: строка получает безопасный
   конфликт `product_factory_conflict`, остальные строки страницы продолжают
   обрабатываться. Разрешение конфликта требует проверки identity.

Для существующих данных отдельная повторяемая команда
`jv:aftercool:backfill-product-factories` использует
`jv_aftercool_product_source` и сохранённые имена фабрик из завершённых run.
Она не делает запросов к Aftercool и не выбирает произвольную фабрику при
нескольких разных ID у одного товара: такие товары попадают в отчёт конфликтов.
Если локального имени для ID нет, запись остаётся без новой связи до
подтверждённого повторного импорта. Повторно используемая локальная фабрика
находится через source mapping; импортное имя синхронизируется с последним
сохранённым именем run. Миграция схемы не выполняет массовый перенос данных.
После каждого пакета DAL-обновлений команда запускает штатный product
indexer, включая обновление `product_stream_mapping`.

## Динамические группы

Administration предлагает DAL association `jvFactory` как поле условия
product stream с оператором `equals` и селектором `jv_factory.id`. Условие
хранит стабильный UUID фабрики, а не её название или внешний Aftercool ID.
Селектор получает только сохранённые `jv_factory`; редактирование stream
не вызывает Aftercool API. Поскольку установленная Shopware Administration
исключает product associations из стандартного allowlist product-stream,
`JvImport` добавляет только association `jvFactory` в этот allowlist; список
идентификаторов селектора читает штатный DAL `jv_factory.repository`.
Пример фильтра: `field = jvFactory.id`,
`type = equals`, `value = <factory UUID>`.

После изменения связи товара штатный индексатор Shopware обновляет
`product_stream_mapping`. Пока асинхронная индексация не завершена, применение
шаблона опций может отражать предыдущее состояние; отдельного синхронного
lookup в Aftercool или обхода `product_stream_mapping` не вводится.
Принадлежность stream варианту и приоритет ручного назначения шаблона остаются
по SPEC-054.

## Ошибки и совместимость

ID фабрики Aftercool проверяется на границе API по SPEC-013. Уникальные
ограничения и FK не позволяют создать две локальные записи для одного source
ID или сохранить ссылку на отсутствующую фабрику. Импорт не пишет raw response
и credentials в фабричные сущности, ошибки или лог.

Изменение аддитивно: существующие товары без связи сохраняют прежнее
поведение, существующие manufacturer и шаблоны опций не переписываются.
Порядок выпуска: миграция схемы, установка/обновление плагина, backfill,
индексация, затем создание новых product streams. Откат кода не должен
удалять каталог фабрик или связи из базы.

## Проверка

Автоматические тесты через DAL и зарегистрированные сервисы проверяют:

- список/preview/queued run не создают локальную фабрику;
- первый успешный импорт создаёт ровно одну фабрику и связывает товар,
  сохраняя `manufacturer=JVMOEBEL`;
- пустая страница и все ошибочные строки не создают фабрику;
- повтор страницы/импорта не дублирует фабрику или source mapping;
- переименование при прежнем ID меняет имя, не UUID; одинаковые имена при
  разных ID не объединяются;
- write failure и конфликт фабрик не оставляют частичных связей;
- backfill повторяем, не вызывает внешний API и сообщает неоднозначность;
- фильтр `jvFactory.id equals` включает только товар нужной фабрики,
  исключает остальные и обновляется после смены связи; вариант наследует
  связь родителя;
- повторяемая команда backfill восстанавливает связь и membership из сохранённых
  source links; конфликт нескольких внешних фабрик одного товара выводится в
  отчёт без выбора одной из них;
- шаблон опций через stream применяется к нужному товару, а ручное назначение
  сохраняет приоритет.

Ручная приёмка: импортировать одну фабрику, открыть Administration product
stream, выбрать «Фабрика → equals» из локального списка, назначить stream
шаблону опций и проверить Store API товара, корзину и товар другой фабрики.
После переименования фабрики проверить сохранность условия и membership.
