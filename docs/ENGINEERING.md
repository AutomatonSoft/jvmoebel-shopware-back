# Engineering guidelines

Правила применяются к собственному коду JVMöbel. Код Shopware и сторонних расширений не изменяется и не переформатируется.

## Основные принципы

- Класс имеет одну понятную ответственность.
- Use case выполняет один законченный прикладной сценарий.
- Зависимости направлены от входных точек к application-сервисам и далее к Shopware DAL или контрактам интеграций.
- Наследование используется только когда оно требуется Shopware или действительно выражает заменяемое поведение. В остальных случаях используется композиция.
- Интерфейс описывает границу или точку заменяемости, а не создаётся автоматически для каждого класса.
- Решение остаётся настолько простым, насколько позволяет задача. Абстракция добавляется после появления конкретной ответственности.

SOLID применяется как набор правил проектирования, а не как требование создавать дополнительные слои и классы.

## PHP

- Каждый PHP-файл начинается с `<?php declare(strict_types=1);`.
- Код соответствует PSR-12 и форматируется единым конфигом PHP-CS-Fixer.
- Аргументы, свойства и возвращаемые значения типизированы.
- `mixed` используется только на внешней границе, где тип невозможно определить заранее. После чтения внешние данные преобразуются в известную структуру.
- Сложный массив заменяется DTO. Для небольшого технического массива указывается PHPStan array shape или generic type.
- Свойства объявляются `readonly`, если их состояние не должно меняться после создания объекта.
- Классы объявляются `final`, если они не являются предусмотренной точкой расширения.
- Для конечного набора значений используется enum вместо строковых или числовых констант.
- `null` отражает допустимое отсутствие значения, а не ошибку или неизвестный тип.
- PHPDoc дополняет систему типов и объясняет контракт. Он не повторяет сигнатуру или очевидное поведение.
- Комментарий объясняет причину нетривиального решения, а не пересказывает код.

## Имена и размер классов

- Имя use case состоит из действия, объекта и суффикса `Service`: `ImportProductsService`, `AssignCategoriesService`, `RebuildSeoUrlsService`.
- Общие имена `Manager`, `Helper`, `Util` и `Processor` используются только при наличии точной и ограниченной ответственности.
- Controller, subscriber, console command и message handler не содержат основной сценарий.
- Use case имеет одну основную публичную операцию, обычно `execute()`.
- Framework handlers используют ожидаемый фреймворком entry point, например `__invoke()` для Messenger.
- Приватный метод выделяется для самостоятельного шага, а не только ради уменьшения количества строк.

## Зависимости

- Зависимости передаются через constructor injection.
- Прикладной код не обращается к контейнеру Symfony и не использует service locator.
- Сервисы регистрируются через конфигурацию плагина; скрытое создание инфраструктурных зависимостей внутри метода не допускается.
- Изменяемое состояние не хранится в static-свойствах и глобальных переменных. Singleton pattern не реализуется вручную.
- Время, генератор идентификаторов и другие изменчивые зависимости передаются явно, когда они влияют на результат и тестирование.

## Application-сервисы

- Входная точка преобразует HTTP request, message или console input в типизированные аргументы/DTO и вызывает use case.
- Use case координирует проверки, DAL, очередь и интеграции, но не разбирает формат внешнего источника.
- Транзакция начинается на уровне сценария, которому требуется атомарность нескольких изменений.
- Повторный запуск команды или message handler не должен создавать дубли или повторять завершённый побочный эффект.
- Правила, влияющие на результат операции, находятся в application-сервисе или специализированном validator/policy, а не в controller или subscriber.

## Валидация и преобразование данных

- Входной слой проверяет форму запроса и обязательные параметры.
- Интеграция проверяет структуру внешних данных и преобразует их в DTO проекта.
- Application-слой проверяет бизнес-правила сценария.
- DAL проверяет ограничения сохраняемых полей и связей.
- Symfony Validator используется для DTO и объектов. Shopware `DataValidator` используется для массивов данных, когда это соответствует API Shopware.
- Ошибка преобразования содержит имя поля, источник и безопасный идентификатор записи, если они известны.
- Правила валидации CMS elements, их размещение и подключение в Administration и серверном слое следуют [SPEC-021](specs/SPEC-021-cms-validation.md). Сохранение CMS-страницы блокируется только явно объявленным правилом; по умолчанию ошибка остаётся информационной.

## Shopware и Symfony

- Используются штатные extension points Shopware: DAL, events, subscribers, routes, services, migrations, scheduled tasks и Messenger.
- Ядро Shopware, `vendor/` и сторонние плагины не изменяются и не копируются в проект.
- Для чтения и записи сущностей используется DAL. Прямой SQL требует технического обоснования и параметризованных запросов.
- `Context` передаётся явно. Для поведения, зависящего от магазина или покупателя, используется соответствующий `SalesChannelContext`.
- Конфигурация, зависящая от рынка, читается с учётом sales channel.
- Изменение схемы выполняется миграцией плагина.
- Store API route возвращает типизированный response и следует механизму route scope Shopware.
- Декорирование стандартного поведения выполняется через предусмотренный Shopware decoration pattern.

## Ошибки

- Application-исключения размещаются в `Service/<Feature>/Exception/`; исключения внешнего источника или API — в `Integration/<Name>/Exception/`.
- Исключение обозначает конкретную причину и содержит контекст, необходимый вызывающему коду.
- Низкоуровневая ошибка не скрывается. При преобразовании исключения исходное исключение передаётся как `previous`.
- `catch (\Throwable)` используется только на границе процесса, где необходимо сформировать ответ, отчёт или решение о повторе.
- Ожидаемая ошибка входных данных отличается от временной ошибки инфраструктуры и программной ошибки.
- Пакетная операция сообщает об ошибках отдельных записей и не объявляет частичный результат полным успехом.
- Публичный API не возвращает stack trace, внутренние пути, SQL или секретные данные.

## Логирование

- Код использует `Psr\Log\LoggerInterface` и структурированный context.
- Запись содержит операцию, environment, correlation/run ID и идентификаторы сущностей, необходимые для поиска причины.
- Ошибка логируется один раз на границе, которая принимает решение о завершении, retry или пропуске записи.
- Пароли, токены, платёжные данные, содержимое cookies и персональные данные не логируются.
- Ожидаемая ошибка валидации не записывается как системная ошибка.

## Интеграции и фоновые процессы

- Внешний вызов имеет timeout и обрабатывает сетевую ошибку, недоступность сервиса и некорректный ответ.
- Retry применяется только к временной ошибке и не нарушает идемпотентность операции.
- Долгая работа выполняется через Messenger или scheduled task, а не внутри HTTP-запроса.
- Message содержит идентификаторы и параметры операции, а не большой сериализованный объект или чувствительные данные.
- Handler может безопасно получить актуальное состояние после задержки между отправкой и обработкой сообщения.

## Статический анализ и форматирование

- PHPStan запускается минимум на уровне 6 без новых ошибок.
- PHPStan baseline, ignore и подавление ошибки требуют объяснения в коде или pull request.
- PHP-CS-Fixer проверяет единый стиль собственного PHP-кода.
- Правило анализа или форматирования не отключается локально без технической причины.

Корневой `composer.json` предоставляет единые команды:

```bash
composer lint
composer format
composer analyse
composer test
```

`lint` только проверяет форматирование; `format` изменяет файлы. Эти же команды используются локально и в CI.

## Тестирование

- Изменённое прикладное поведение покрывается автоматическими тестами.
- Use cases, validators, normalizers и value objects покрываются unit-тестами.
- DAL, миграции, DI-конфигурация плагина, subscribers и message handlers проверяются integration-тестами.
- Store API routes и права доступа проверяются functional-тестами.
- Исправление дефекта сопровождается тестом, воспроизводящим дефект, если это возможно на соответствующем уровне.
- Автоматический тест не обращается к production и реальному внешнему сервису. Интеграция заменяется fake или stub на границе её контракта.
- Тест проверяет успешный сценарий, значимые ошибки и повтор операции, если она может выполняться асинхронно.
- Миграция проверяется на существующей схеме и данных, а не только на пустой базе.

Тесты собственного плагина находятся в его каталоге `tests/` и повторяют функциональные области кода.

```text
tests/
├── Unit/
├── Integration/
└── Functional/
```

## Безопасность

- Секреты и конфигурация окружения не хранятся в коде, fixtures, логах или Git.
- Права Admin API и Store API проверяются на каждой новой входной точке.
- Данные sales channel и customer context не принимаются из запроса без проверки Shopware context.
- Пользовательские значения не подставляются в SQL, команды оболочки, пути файлов и URL без проверки и безопасного экранирования.
- В код и отчёты попадает только необходимый объём персональных данных.
