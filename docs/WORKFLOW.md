# Backend workflow

Ветвление, release flow, требования к review и работа с Git определяются в репозитории `jvmoebel-shopware-docs`. Этот документ описывает подготовку и проверку изменений Shopware backend.

## Подготовка задачи

До разработки должны быть определены:

- ожидаемый результат;
- затрагиваемый плагин и функциональная область;
- критерии приёмки;
- изменения данных, API, очереди и конфигурации;
- необходимость backend specification и общего ADR.

Specification создаётся или обновляется до реализации изменения публичного поведения, формата данных, интеграции, импорта, сообщения очереди или сценария с несколькими потребителями.

## Реализация

Изменение выполняется в пределах одной функциональной задачи. Связанный рефакторинг допускается, если он необходим для реализации и проверяется в том же pull request.

Последовательность работы:

1. Обновить specification и миграции, если меняются контракт или схема данных.
2. Реализовать application-сценарий и необходимые входные точки/интеграции.
3. Добавить или обновить автоматические тесты.
4. Выполнить локальные проверки проекта.
5. Обновить backend-документацию, если изменились правила или структура.

Несвязанные исправления, массовое форматирование и обновление зависимостей выполняются отдельными задачами.

## Локальная проверка

Перед открытием или обновлением pull request обязательные проверки запускаются **в контейнере** `web`: на хосте им нужны PHP 8.5, MySQL и OpenSearch, которых в свежем окружении обычно нет.

```bash
docker compose exec -T web composer lint
docker compose exec -T web composer analyse
docker compose exec -T web composer test
```

`composer format` (также в контейнере) используется для исправления форматирования перед повторным запуском `composer lint`. Эти же команды используются локально и в CI (GitHub Actions workflow `.github/workflows/ci.yml` на pull request в `develop` и `main`).

Для изменения Store API, Administration или фонового процесса дополнительно выполняется ручной сценарий на локальном окружении либо staging с подходящими тестовыми данными.

## Миграции и данные

- Миграция схемы запускается на базе с существующими данными.
- Миграция не рассчитывает на пустую установку и не удаляет рабочие данные без отдельного согласованного плана.
- Массовое изменение данных выполняется отдельной командой или импортным процессом.
- Команда и message handler поддерживают безопасный повторный запуск.
- Pull request описывает порядок применения и отката релиза, если изменение несовместимо с предыдущим кодом.

## Pull request

Описание pull request содержит:

- результат изменения;
- затронутые плагины и функциональные области;
- изменения схемы, конфигурации, очередей и внешних интеграций;
- инструкцию проверки;
- выполненные автоматические и ручные проверки;
- ссылки на specification и ADR.

Generated files добавляются только когда они являются частью поставляемого расширения и воспроизводимо собираются из исходного кода.

## Готовность к merge

Изменение готово к merge, когда:

- выполнены критерии приёмки;
- код соответствует `ARCHITECTURE.md` и `ENGINEERING.md`;
- `lint`, `analyse` и `test` проходят;
- миграции и фоновые процессы проверены на повторный запуск;
- specification соответствует реализованному поведению;
- pull request содержит достаточную инструкцию для проверки и выпуска.
