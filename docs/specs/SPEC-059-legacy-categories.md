# SPEC-059 — Архив категорий старых CosmoShop-проектов

## Цель и основание

Сохранить дерево категорий каждого старого CosmoShop-проекта внутри Shopware как самостоятельный исторический справочник. Оператор однократно загружает снимок проекта и явно выбирает принадлежащий ему sales channel. Администратор просматривает дерево и исходные данные в отдельном разделе Administration.

Решение развивает принятый `jvmoebel-shopware-docs/docs/adr/ADR-001-data-source-ownership.md`: старые категории сохраняются для проверки миграции и SEO, но не становятся целевым деревом. Это backend-локальная задача: Store API, публичные URL и Next.js не меняются.

## Границы и ответственность

Входят новый плагин `JvLegacyCatalog` в `custom/static-plugins/`, его сущности, миграции, команда загрузки файла, Admin API только для чтения и Administration-раздел. Плагин самостоятельно владеет архивом и импортом; зависимость от `JvImport` не требуется.

Не входят создание или изменение штатной Shopware `category`, navigation tree, product assignments, CMS pages, SEO URL, sitemap, Store API; связь старой категории с новой, автоматический mapping и redirects; импорт товарных связей `shoprubrikartikel`; постоянное соединение Shopware со старой БД и синхронизация; редактирование архива через Administration.

`JvImport` и `JvSeo` не читают таблицы архива напрямую. Будущий потребитель получает отдельный контракт чтения и объявленную одностороннюю зависимость. Команда сопоставления из [SPEC-053](SPEC-053-product-legacy-redirects.md) пока читает старую БД; её перевод на архив — отдельная задача и не меняет этот импорт.

## Термины и идентичность

- **Исходный проект** — один старый сайт/БД. `source_project` — заданный оператором стабильный ключ, например `jvmoebel.de`. Он не выводится из имени БД или Shopware channel.
- **Снимок** — неизменяемая пара `manifest.json` и `categories.jsonl` из одного согласованного состояния исходной БД.
- **Привязка** — один `source_project` соответствует ровно одному выбранному sales channel в данной установке. Один канал может иметь больше одного источника; интерфейс всегда показывает источник.
- **Исходный ID** — `shoprubriken.rubid`, уникальный только в рамках исходного проекта. Одинаковые `rubid` разных проектов не конфликтуют.

Sales channel выбирается человеком по Shopware ID при запуске команды. До записи команда показывает ID, имя и домены найденного канала. Принимается только существующий Storefront sales channel. По домену, имени файла или данным категории канал не угадывается. Ключ проекта одинаков между средами; Shopware ID канала выбирается в каждой среде отдельно. Повторная привязка проекта к другому каналу отклоняется.

## Сценарий

1. Внешний read-only скрипт создаёт пару файлов для одного исходного проекта. Оператор архивирует её вне Git как неизменяемый артефакт.
2. Оператор запускает `jv:legacy-catalog:import-categories <manifest-file> --sales-channel-id=<uuid> --dry-run`. Команда проверяет весь снимок, checksum, структуру дерева и существующую привязку без записи.
3. Оператор сверяет source project, канал, checksum и counts, затем запускает ту же команду без `--dry-run`.
4. Плагин атомарно сохраняет источник, категории, языковые данные и связи дерева; выводит reconciliation report.
5. В Administration оператор выбирает канал и источник, просматривает дерево, ищет категории и открывает детали.

Штатный Shopware Import/Export не используется: требуется проверка законченного снимка дерева до первой записи.

## Контракт входного файла

### Manifest v1

UTF-8 JSON-объект с обязательными полями:

| Поле | Значение |
|---|---|
| `format` | строка `jv-legacy-categories` |
| `version` | число `1` |
| `source_system` | строка `cosmoshop` |
| `source_project` | непустой стабильный ключ, максимум 120 символов |
| `categories_file` | относительное имя `categories.jsonl`; path traversal запрещён |
| `categories_sha256` | SHA-256 точных байтов JSONL, lowercase hex |
| `category_count` | количество категорий |
| `content_count` | количество строк `shoprubrikencontent`, присоединённых к категориям |
| `seo_count` | количество присоединённых строк `shopseo` типа `r` |

Manifest не содержит Shopware `sales_channel_id`: выбор выполняется при импорте. Диагностические поля времени экспорта, имени БД и количества orphan SEO допустимы, но не определяют идентичность или привязку. Неизвестная версия отклоняется; смысл полей v1 не меняется без новой версии.

### categories.jsonl

UTF-8 JSON Lines: по одной категории в строке, без пустых строк, по возрастанию `rubid`. Обязательная структура записи:

~~~json
{
  "source_category_id": 123,
  "source_parent_id": 0,
  "rubric": {"rubid": 123, "parentid": 0, "rubnum": "..."},
  "content": [
    {"rubid": 123, "rubsprache": "de", "rubnam": "...", "urlkey": "..."}
  ],
  "seo": [
    {"typ": "r", "id": 123, "sprache": "de", "page_title": "..."}
  ]
}
~~~

`rubric` содержит все колонки исходной строки `shoprubriken` с исходными именами; `content` — все строки `shoprubrikencontent` этой категории со всеми колонками; `seo` — все её строки `shopseo` с `typ='r'` со всеми колонками. SQL NULL передаётся JSON null, ID — целым числом, текст — UTF-8 без trim, HTML-очистки, перевода или slugification. Бинарные значения, включая `mega_menu`, передаются объектом `{"base64":"..."}`; пустой BLOB отличается от SQL NULL. MySQL zero-date остаётся исходной строкой. Отношения с товарами не добавляются.

Похожие сайты могут иметь разные дополнительные столбцы: они сохраняются в raw-объектах без потерь. v1 требует как минимум `rubid`, `parentid`, `rubnum` в `rubric`; `rubid`, `rubsprache`, `rubnam`, `urlkey` в каждой строке `content`; `typ`, `id`, `sprache`, `page_title`, `meta_description`, `meta_keywords` в строке `seo`. Проект без таблицы `shopseo` допускает пустые массивы `seo` и явную отметку в отчёте экспортёра. Отсутствие обязательной таблицы или колонки требует новой версии контракта либо отдельного утверждённого правила.

Исходные коды языков сохраняются без преобразования в Shopware language. URL keys не становятся активными URL или redirects.

## Данные Shopware

### jv_legacy_catalog_source

Собственная DAL entity: ID, `source_system`, уникальный `source_project`, обязательный FK на `sales_channel`, версия формата, SHA-256 файла, заявленные и фактические counts, время импорта и системные timestamps. При удалении sales channel с архивом FK запрещает потерю привязки до отдельного плана переноса/удаления.

### jv_legacy_category

Собственная DAL entity: ID, FK на source, исходные `rubid` и `parentid`, nullable FK `parent_id` на категорию того же source, исходный `ruborder`, индексируемые отображаемое имя и URL key, полная исходная строка `rubric` в JSON. Уникальность `(source_id, source_category_id)`; индекс `(source_id, parent_id)`. Для дерева имя берётся из непустого немецкого `rubnam`, затем первого доступного языка, затем `rubnum`, затем `#<rubid>`. URL key для списка берётся из выбранного content, затем `ruburlkey`. Raw данные не меняются.

### jv_legacy_category_content

Собственная DAL entity: ID, FK на категорию, исходный код языка, поля `rubnam`, `rubtext`, `rubtext_kurz`, `urlkey`, `page_title`, `meta_description`, `meta_keywords` и raw JSON исходных content/SEO строк. Уникальность `(category_id, source_language)`. SEO без content того же языка сохраняется в отдельной языковой строке с пустыми content-полями; категория без content тоже сохраняется.

Orphan `shopseo` с `typ='r'` без категории не создают фиктивный узел: экспортёр сообщает их число. Их отдельное хранение вне категорий выходит за границы этой задачи. В архиве нет FK на штатные `category`, `product` или `seo_url`.

## Валидация, ошибки и повтор

- До записи проверяются manifest/JSONL, UTF-8, версия, checksum, counts, обязательные типы и отсутствие дубликатов `rubid`.
- `rubric.rubid`, `content.rubid` и `seo.id` совпадают с `source_category_id`; `seo.typ` равен `r`. В категории не бывает двух content или SEO строк одного языка.
- `parentid=0` означает корень. Другой parent обязан существовать в том же снимке; self-parent и цикл запрещены. Порядок детей и корней: `ruborder`, затем `rubid`.
- Любая ошибка строки или привязки отклоняет весь снимок без частичных данных. Диагностика указывает номер строки, source ID и правило; сырой HTML и секреты не логируются.
- Первое применение атомарно сохраняет снимок. Точный повтор для того же проекта, канала, версии и SHA-256 возвращает `already_imported` без записи. Другой checksum/версия уже импортированного проекта отклоняется; исправление снимка требует отдельного плана.
- Конкурентные запуски защищены уникальными ограничениями и транзакцией. `--dry-run` проходит ту же валидацию, но ничего не записывает.

Отчёт содержит проект, ID/имя/домены канала, checksum, counts категорий/корней/content/SEO, число категорий без content/SEO, доступные diagnostic counts экспортёра и статус `valid|imported|already_imported|rejected` с причиной.

## Administration

Отдельный пункт `Каталог → Исторические категории` требует права чтения legacy catalog. Основная карточка занимает доступную ширину страницы. На странице есть селектор sales channel, при необходимости — source project, счётчики и дерево. При выборе source всё его дерево загружается постранично до отображения; ветки изначально свёрнуты, а сворачивание и раскрытие уже загруженных веток не выполняет новых запросов. Поиск по имени, `rubid`, `rubnum` и URL key ограничен выбранным source и приводит к узлу с цепочкой предков. Дерево и результаты поиска размещены во вкладках; обе панели остаются загруженными, а после запуска поиска автоматически открывается вкладка результатов. Рядом с узлом дерева и результатом поиска есть ссылка на отдельную страницу данных категории, которая открывается в новой вкладке.

Единственная боковая панель справа закреплена при прокрутке страницы и показывает детали выбранной категории; при выборе другой категории содержимое панели заменяется. Под именем показывается полный URL категории как активная ссылка с доменом sales channel и URL keys всех предков; URL вычисляется при чтении и не сохраняется в БД. Для вложенной категории с подкатегориями URL заканчивается `/`; у корневой категории и конечного узла завершающего `/` нет. Иконка рядом с подписью копирует URL в буфер обмена. На отдельной странице открываются те же полные детали. Детали показывают путь, исходные ID и порядок, все языки, тексты, URL key, SEO и прочие raw поля. HTML и бинарные значения не исполняются и не встраиваются в DOM: выводятся как текст или обозначение размера/base64. Пустые поля видны явно. Нет кнопок создания, редактирования, удаления и перетаскивания. Backend предоставляет только защищённые Admin API чтения; запись возможна только консольной командой. Store API отсутствует.

Визуальные компоненты Shopware можно переиспользовать, но экран не обращается к штатному category repository и не изменяет его данные.

## Изменения проекта и выпуск

`JvLegacyCatalog` содержит plugin class, Composer registration, DAL definitions, миграцию схемы, use case импорта, JSONL reader/normalizer, команду, Admin API чтения, Administration UI и право чтения. Миграция создаёт только схему. Загрузка выполняется после установки плагина и создания нужного sales channel. Файлы и credentials не попадают в Git. После изменения Administration собираются production assets по WORKFLOW.md. Откат кода не удаляет архивные данные; очистка ошибочной привязки — отдельная управляемая операция.

## Отдельный блок: внешний скрипт выгрузки старых категорий

Скрипт **не входит в backend-репозиторий** и не запускается внутри плагина. Он читает один старый проект и формирует файловый контракт выше. Его реализация и тесты — отдельная задача в контуре миграционных инструментов; версию скрипта и инструкцию запуска сохраняют там же. Файлы, checksum и отчёт каждого запуска хранятся вне Git в защищённом migration storage.

Требования к скрипту:

1. Принимать явные параметры подключения к одной старой БД, `source_project` и каталог вывода. Sales channel не выбирать.
2. Использовать read-only пользователя и замороженную копию исходной БД; для живой БД согласованность чтения обеспечить отдельно, так как таблицы могут иметь разные storage engines. Читать `shoprubriken`, все относящиеся `shoprubrikencontent` и `shopseo` с `typ='r'`. Не смешивать проекты и не писать в источник.
3. Сериализовать все колонки без потерь, бинарные поля через base64; сортировать категории по `rubid`, языковые строки по коду языка. Повторный экспорт одного состояния даёт byte-identical JSONL и SHA-256.
4. После закрытия JSONL вычислять counts и checksum и формировать manifest. Отдельный отчёт показывает корни, missing parents, cycles, duplicate IDs/languages, категории без content, orphan content/SEO. Ошибка чтения или обязательной схемы не публикует частичный набор.
5. Писать временные файлы и публиковать финальную пару только после успеха. Не перезаписывать архивированный снимок с другим checksum. Пароли не передавать в аргументах команды, manifest, данных и логах.

## Проверка и критерии приёмки

- Два проекта с одинаковыми `rubid` импортируются независимо и видны только при выборе своего sales channel/source.
- Неизвестный или не-Storefront канал, перепривязка проекта, неверный checksum, дубликат ID, отсутствующий родитель и цикл отклоняются без частичных записей.
- Dry-run не меняет БД; первый импорт сохраняет ожидаемые counts; точный повтор возвращает `already_imported`, изменённый снимок отвергается.
- Категория без content, SEO отдельного языка, пустой URL key и бинарное поле сохраняются и просматриваются без потери source значения.
- Экран и Admin API не предоставляют запись; без права чтения они недоступны. Штатное дерево каталога и Store API не меняются.
- Для локального `old_mebel` ориентир до экспорта: 699 категорий, 697 строк `shoprubrikencontent` языка `de`, 697
  присоединённых SEO-строк типа `r` и 214 orphan SEO-строк (read-only аудит
  25.09.2026). Это не требование к другим сайтам.
- Unit/integration tests проверяют reader, валидацию, атомарность, DAL, привязку канала, права Admin API и повтор. Ручной сценарий проверяет дерево, поиск и детали с двумя источниками.
- Перед PR в контейнере `web` выполняются `docker compose exec -T web composer lint`, `composer analyse` и `composer test`; Administration assets собираются `bin/build-administration.sh` и сверяются с Git.
